# Crate favorites

## What we are building

A signed-in collector can favorite any crate they do not own. They do it from that crate's own page, `/crates/:id`. Their favorites then appear on their profile in a **Favorites** section. The section is separate from the **Crates** section, which keeps listing only crates they created. This is the first "bookmark someone else's work" feature in Frisson. Until now the only social link was following another collector.

## Why it is shaped this way

The codebase already has a close model in Follows, which is a user-to-user relation. It has its own table, idempotent PUT/DELETE routes that return 204, a `signedInOnly` preValidation hook so signed-out callers get 401 before any 400, a thin route over a plain-function service, and a non-optimistic toggle button in the web app. Favorites are the same pattern as a user-to-crate relation. Copying it keeps the API predictable and lets reviewers compare the two features directly.

### Data

A new `crate_favorites` table holds `id, user_id, crate_id, created_at`. It has a unique index on `(user_id, crate_id)`, so favoriting twice leaves one row, and a secondary index on `crate_id`. Both foreign keys use `ON DELETE CASCADE`, so deleting the user or the crate removes the rows. A crate can only be deleted once it is empty, so the cascade must not block a delete that would otherwise succeed. Migration `0006_crate_favorites.sql` is generated by drizzle-kit and only creates the table and its indexes. Earlier migrations are untouched, and a migration test confirms that a DB at 0005 keeps every user and crate row after upgrading.

### API

- `PUT /api/crates/:id/favorite` and `DELETE /api/crates/:id/favorite` act only for `request.user`, and no route sets favorites for anyone else. Both return 204 and are idempotent. The signed-in check runs in preValidation, so a signed-out caller gets 401 even with a non-numeric id. An unknown crate gives 404. Favoriting your own crate gives 400 and writes nothing. "Not yours" means `crate.ownerId !== viewer.id`, so ownerless legacy crates and demo crates can be favorited. An admin can favorite other people's crates but not their own.
- `GET /api/crates/:id` gains `viewerFavorited: boolean`. It is false when signed out. It lives in a new `crateDetail` schema used only by this route, so the shelf list and the create, update and delete responses stay the same shape.
- `GET /api/users/:username` (`publicProfile`) gains `favorites`, newest favorited first. Each entry is a `profileFavorite` with exactly `id, name, label, color, albumCount, ownerUsername, ownerDisplayName`. The owner fields are nullable for ownerless crates. Under the public-data rule these cards never carry an email, role, numeric user id or demo key. The service selects only those columns, and the Zod response schema strips anything else. `crates` remains owner-only.

### Web

- **Crate page.** On `/crates/:id` only (not `/shelf`, Home or the Following feed), a signed-in viewer who does not own the crate sees a toggle button named "Favorite". Its `aria-pressed` reflects `viewerFavorited`. CrateView fetches `GET /api/crates/:id` for that state, because the library store's crate list does not carry it. Like FollowButton, the button changes state only after the server agrees, and a failure shows an inline alert. Signed-out viewers and owners see no control, and there is no "log in to favorite" prompt. Existing crate-page behaviour stays as it is: toolbar actions remain hidden on other users' crates, and edit gating and spin counting are unchanged.
- **Profile.** ProfileView, which serves both `/u/:username` and `/profile`, adds a Favorites section after Crates. The cards look like the Crates cards, plus a plain-text "by <owner display name>" line. The section shows "No favorites yet." when empty. The cards use the same stretched-link technique, and each card contains its own overlay. That way neither section swallows clicks meant for the other, which was a past source of bugs. The owner name is text rather than a nested link for the same reason. All user text is rendered with `{{ }}`.

### Public vs private

The brief assumes favorites are public, like the Crates section and unlike follow lists. This is the assumption most likely to be wrong. It is recorded in ADR 0008 so it is easy to find and reverse. Making favorites private would be a small change: drop `favorites` from `publicProfile` for non-owners, and show the section only to the profile owner.

## Out of scope

There are no favorite counts, no notifications to crate owners, no `/me/favorites` endpoint, and no favorite control on cards outside the crate page. If an admin later reassigns a crate to someone who had favorited it, their old favorite row stays.

## Work split

1. **T1, backend (opus).** Shared schemas, the table and generated migration, the service, routes, profile and crate-detail changes, API and migration tests for AC1-AC6, and the `favorites: []` additions to existing web test fixtures so typecheck stays green.
2. **T2, crate page (opus, after T1).** Web API client, FavoriteButton, CrateView wiring and component tests for AC8. It also updates any CrateView-related fetch mocks that the new GET call disturbs.
3. **T3, profile and docs (sonnet, after T1, parallel with T2).** The ProfileView Favorites section and tests for AC7, plus updates to README, SPEC, DEPLOY and ADR 0008.

AC9 and AC10 are browser criteria. T2 and T3 build what they exercise, and the browser tester writes and runs those checks on a temp DB copy under `.shipyard/checks/`. No dev task touches `.shipyard/`, starts a dev server, or touches `data/crate.db`. AC11 (typecheck, lint, test) applies to every task.
