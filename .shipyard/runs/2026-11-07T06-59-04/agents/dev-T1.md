## What changed

- `packages/shared/src/index.ts`: new Accounts section with `USER_ROLES`, `publicUser` (no password field), `signupInput` and `credentialsInput`, plus the types `UserRole`, `PublicUser`, `SignupInput` and `CredentialsInput`.
  - `signupInput`: email is trimmed, lower-cased and checked with `z.email`, max 254. Username is trimmed, lower-cased, 3-32 characters of `[a-z0-9_-]`. `displayName` is optional, trimmed, 1-60. Password is min(8, 'At least 8 characters') and max(200).
  - `credentialsInput`: password min(1) and max(200).
  - Both are plain `z.object`, so unknown keys such as `role` are stripped.
  - The crate schema gains the three owner fields. `sessionInfo`, `loginInput` and `SessionInfo` are kept.
- `apps/api/src/db/schema.ts`:
  - `users` table: unique email and username, `display_name`, `password_hash`, a `role` enum defaulting to 'user', and `created_at`.
  - `sessions` table: text pk (sha256 hex), `user_id` FK with cascade, `created_at`, `expires_at`, and the index `sessions_user_id_idx`.
  - `crates.owner_id` FK to users with set null.
  - New relations and inferred types. Data-classification comments added.
- `apps/api/drizzle/0003_accounts.sql`, `meta/0003_snapshot.json` and `meta/_journal.json`: generated by `npm run db:generate -w apps/api -- --name accounts`. The SQL was not edited. The two JSON files were run through Prettier, which format:check requires, as it did for the earlier snapshots. A second `npx drizzle-kit generate` reports "No schema changes".
- `apps/api/src/services/crates.ts`: `crateColumns` adds `ownerId`, `ownerUsername` and `ownerDisplayName` via a LEFT JOIN on users in `listCrates` and `getCrate`. It still groups by crates.id. No authorization logic.
- `apps/api/src/services/passwords.ts`: uses node:crypto `scrypt` (async, N=16384 r=8 p=1, 64-byte key, maxmem 32 MiB) with a fresh 16-byte salt per hash.
  - Hash format: `scrypt$N$r$p$saltB64$hashB64`.
  - `hashPassword` throws `HttpError(400)` for passwords under 8 characters.
  - `verifyPassword` parses strictly and returns false on malformed input: wrong prefix or part count, empty parts, N not a power of two, or out-of-range parameters. It compares with a length check plus `timingSafeEqual`.
  - `verifyAgainstDummy(plain)` checks against a lazily created random hash and always resolves false.

It migrates a temp file DB with only 0000-0002 (3-entry journal, FKs ON) and inserts rows with bound statements. ## Finding for the owner and tester

drizzle-kit's ALTER does not carry the FK action: `ALTER TABLE crates ADD owner_id integer REFERENCES users(id);` has no `ON DELETE SET NULL`. In real databases the FK is therefore NO ACTION, while schema.ts and the snapshot say set null. Deleting a user who owns crates will fail with a FK error until a later migration rebuilds crates. User deletion is out of scope this cycle. I did not hand-edit the SQL, per the rules.
